안녕하세요, MLOps/Data Scientist 정현수입니다.

저는 운영 현장의 문제를 데이터·머신러닝·서버리스 시스템으로 해결해 실제 성과로 연결하는 MLOps/Data Scientist입니다. 데이터 분석에 머무르지 않고, 문제 정의 → 데이터 파이프라인 → 모델링 → 최적화 알고리즘 → 클라우드 배포 → 운영 모니터링까지 End-to-End로 구현하는 경험을 쌓아왔습니다.

딜리버스(Delivus)에서는 당일배송 운영 효율화를 위해 우편번호 기반 클러스터링 엔진, 최대 배송량 예측 모델, 실시간 경로최적화 API, ETA 예측 시스템, 좌표 품질 검증 및 클러스터 밀집도 모니터링 Lambda를 개발·운영했습니다.

우편번호 기반 클러스터링 엔진과 오버랩 클러스터링 알고리즘을 개발하여 클러스터링 시간을 39.5분에서 24.3분으로 38% 단축했고, 평균 배송지 간 거리를 141.3m에서 110.05m로 22% 감소시켜 허브 출차 및 배차 효율 개선에 기여했습니다.

또한 물량·지역·요일 기반 최대 배송량 예측 모델을 운영 파이프라인에 통합해 기사별 적정 물량 산정을 자동화했으며, 이를 통해 전체 배송 권역 SLA를 97.15%에서 97.93%로 약 0.78% 개선했습니다.

이와 함께 ITS 실시간 교통정보 + OSRM + ALNS 기반 경로최적화 시스템을 구축하고, 캐싱과 정수화를 적용해 API 평균 응답시간을 15.55초에서 5.38초로 개선했습니다. 이후 S3/Athena 기반 경로 결과 조회 API와 ETA 계산 Lambda까지 연결하여 운영 시스템에서 바로 활용 가능한 서버리스 MLOps 구조로 확장했습니다.

저는 실제 운영 데이터와 현장 제약을 이해하고, 이를 ML 모델·최적화 로직·AWS 기반 자동화 시스템으로 구현해 운영 효율과 서비스 품질을 함께 높이는 일을 지향합니다.

서비스 기능

  • 회사 DB의 운영 데이터를 기반으로 물량·지역·요일에 따른 총 배송 소요시간 예측
  • 지역별 가용시간과 예측값을 활용해 운영 가능한 최대 배송량(MAX) 자동 산출
  • 기사 스케줄 기반으로 고정/FLEX 기사별 MAX 값 자동 분배
  • AWS Lambda(SAM Image) + EventBridge 기반으로 매일 자동 실행되며, 결과는 Google Sheets에 자동 업데이트되어 운영팀이 즉시 활용

핵심 구현 프로세스

  • 1) DB 직접 연동
    Lambda template.yaml에 VPC Subnet / Security Group 설정을 적용하여 회사 DB에 직접 연결하고, 학습·추론에 필요한 운영 데이터를 조회
  • 2) 데이터 전처리 및 학습
    지역 · 요일 · 물량 · 기사 스케줄 등 운영 데이터를 전처리하고, LightGBM 기반으로 총 배송 소요시간 예측 모델 학습
  • 3) 추론 및 가용시간 결합
    당일 물량과 지역별 조건을 입력으로 추론을 수행하고, 기사 가용시간 및 운영 조건을 결합해 예측 결과 보정
  • 4) MAX 계산
    예측된 총 소요시간과 기사 스케줄을 바탕으로 기사 타입별 최대 배송 가능량 계산
  • 5) 운영 자동화
    SAM 기반 Image 형태로 Lambda에 배포하고, EventBridge 스케줄러로 매일 12:10 클러스터링 이전에 자동 실행되도록 구성
  • 6) 결과 반영
    최종 MAX 값을 Google Sheets에 자동 업데이트하여 운영팀이 클러스터링 직전 의사결정에 바로 활용 가능하도록 구성

    예측된 MAX 값 기반으로 기사별 과·소배차가 감소하면서 전체 배송 권역 SLA가 97.15%에서 97.93%로 약 0.78%개선되었습니다. 지역별 편차가 줄고 지연 리스크가 완화되었습니다.
  • 운영 파이프라인 정착
    단발성 분석이 아닌, Lambda + EventBridge 기반의 일일 자동 실행 구조로 운영 파이프라인에 정착시켜 클러스터링 전 단계에서 항상 최신 기준값이 반영되도록 만들었습니다.
  • DB 직결 기반 안정적 운영
    외부 BI 도구 의존 없이 회사 DB에서 직접 데이터 로딩 → 학습 → 추론이 수행되도록 구성하여 데이터 흐름을 단순화하고 운영 일관성을 높였습니다.
  • 기사 운영 효율 개선
    기사별 처리 가능량을 정량적으로 산출함으로써 적정 작업량 배분이 가능해졌고, 운영팀은 보다 일관된 기준으로 배차 결정을 수행할 수 있게 되었습니다.

  • ITS 실시간 교통정보를 5분 단위로 반영해 도로별 교통량 CSV를 생성하고 OSRM에 반영

  • 캐싱/정수화(Quantization) 적용으로 재호출 시 응답 속도 개선 및 결과 안정성 확보
  • Lambda Function URL 기반 API로 운영 시스템/라이더 앱에서 직접 호출 가능한 형태로 제공

핵심 구현 프로세스

  • 1) Traffic Pipeline
    ITS 실시간 교통 데이터를 5분 단위로 수집·처리하여, 교통량이 반영된 도로별 CSV를 S3에 저장

    S3의 교통량 CSV를 가져와 OSRM segment-speed 데이터로 반영하고, customize 과정을 통해 최신 교통상황이 반영된 OSRM 상태 갱신
  • 3) 기사별 운영 데이터 조회
    프론트엔드로부터 전달받은 기사 ID를 기준으로 회사 DB에서 해당 기사에게 할당된 배송 아이템과 유닛 위치 데이터를 조회
  • 4) Payload 생성 및 Matrix 요청
    조회한 배송지/유닛 데이터를 OSRM 요청용 payload JSON으로 변환하고, 실시간 교통이 반영된 거리 매트릭스(distance matrix) 생성
  • 5) ALNS 기반 최적화
    ALNS를 실행해 방문 순서를 최적화하고, 라이더 앱/운영 시스템에서 사용할 수 있는 ordering/sub_order 형태의 JSON 결과 반환
  • 6) 성능 최적화
    교통량 변화가 없거나 동일 문제 조건일 경우 matrix quantize(정수화) + 캐싱을 활용해 재계산 비용을 줄이고 응답 속도와 재현성 확보

  • 리팩토링 및 성능 개선
